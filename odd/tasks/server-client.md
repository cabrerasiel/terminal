# Server/client split (Rex-style multiplexer and tailnet access)

Objective: move PTYs and layout into a server process so sessions survive the window and can be reached over a tailnet. One branch and one PR per stage, opened from the fork `asielcabrera/terminal-rust` (remote `origin`) to `cabrerasiel/terminal` (remote `upstream`). Test runner: `cargo test`, plus `cargo fmt --all` and `cargo clippy --all-targets -- -D warnings`.

## Specs

- S1 (stage 1) Abstract the pane's byte source: `Pane` depends on a `PaneIo` trait (write, read output, resize, foreground directory, kill, wakeups) instead of the PTY directly. Only implementation: the current local PTY. No visible behavior change; same error messages.
- S2 (stage 2) In-process server: a `server` module owns PTYs, layout and sessions; the window talks to it only through messages (split, close, input, resize, attach).
  - S2a: `server` module on its own thread owns blocks (LocalPty + a server-side libghostty `Terminal` per block, fed with the same bytes, never answering queries). API by messages: create block, write, resize, kill, foreground dir, snapshot. The window uses a new `PaneIo` implementation (`ServerBlock`) backed by these messages. No visible behavior change; same error messages; PTY backpressure preserved.
  - S2b: layout and sessions move to the server (later).
  - Snapshot = libghostty `Formatter` in VT format with scrollback, styles, modes, scrolling region, pwd, keyboard, tabstops; NO palette; followed by an explicit CUP to the real cursor (tabstop sequences move the cursor after the formatter's own CUP).
- S3 (stage 3) Separate server process over local IPC (`terminal server`; Unix socket on macOS/Linux, named pipe on Windows); control channel (length-prefixed JSON, versioned) plus data channel (raw PTY bytes per block, preceded by a screen snapshot). Closing the window keeps shells alive.
- S4 (stage 4) Multiple clients: single input writer, many readers, independent scrollback per client, layout events, resize policy.
- S5 (stage 5) Remote access over the tailnet: 5a HTTP/WebSocket on a Unix socket exposed with `tailscale serve`, identity from Tailscale, owner-only by default; 5b optional embedded Tailscale (`libtailscale`, to verify). "Add remote host" in the app.
- S6 (stage 6, optional) Automation CLI: `ls`, `attach`, `send`, `capture`.

Research (done): `libghostty_vt::fmt::Formatter` with `Format::Vt` reproduces text, scrollback and styles in a fresh terminal. Caveats: tabstop output leaves the cursor in the wrong column (append CUP); only the active screen is exported (primary screen behind an alt-screen app is lost).

## S2b design (locked 2026-11-11)

Authority/projection split: the server owns the authoritative `Layout` + `next_pane_id`; the window keeps a read-only projection rebuilt from server state events. Pure queries (rects, dividers, visible_ids, hit_test, focus, is_float, zoomed, has_floats, float_rect) stay synchronous client-side against the projection — zero async in render/mouse paths. Mutations ONLY via server messages.

- `Layout::state() -> LayoutState` + `Layout::from_state(LayoutState)` (plain data: Node tree, focus, zoomed, floats, floats_visible; no serde needed).
- New message ops: Split{pane,dir,program,explicit}, Close{pane}, SetFocus, FocusDir, FocusCycle, Resize{pane,grow}, SetDivider{..}, ToggleZoom, AddFloat{program,explicit}, ToggleFloats, MoveFloat{pane,x,y}, ResizeFloatEdge{pane,edge,grow}. Server allocates PaneIds, applies the op to Layout, spawns/kills blocks itself (ShellConfig comes in the message), rolls back on spawn failure, and broadcasts one `LayoutEvent::State(LayoutState, Option<CreatedPane>)` per applied mutation (CreatedPane carries the new PaneId + the fully built `ServerBlock` + fallback notice, like create_block does today).
- `LayoutEvent::LastPaneClosed` instead of returning `Closed::LastTiled` (window quits); `LayoutEvent::Error(String)` for spawn failures (window shows the same fallback notice).
- Server does NOT need the window area or cell metrics: the window computes rects from its projection exactly like today's `relayout` and drives PTY resizes through the existing `pane.resize` path. No SetArea message.
- Window: `App.layout` becomes the projection (rebuilt on every State event; never mutated directly); `next_pane_id` moves to the server; `relayout`/render/mouse code reads the projection as before. A debug assertion guards against direct mutation.
- Divider/float drags: each drag step is one message -> one State event -> local relayout (in-process round trip is µs; S3 keeps the same shape over IPC).
- Server tests: split creates the block and reports it, close kills the block and emits LastPaneClosed on the last one, spawn failure rolls the layout back, PaneId allocation is server-owned. Layout's pure tests stay untouched.

## S3 design (locked 2026-11-11)

The in-process server thread becomes a separate `terminal server` process over local IPC; closing the window keeps shells alive; a new window attaches and takes over.

- **Transport abstraction first** (keeps all 167 tests in-process and fast): `ServerHandle` goes over a link (in-process channels today, an IPC connection in stage 3). S2a/S2b machinery reused verbatim.
- **Wire protocol**, one channel pair per connection (Unix socket on mac/linux: mac `~/Library/Application Support/terminal/server.sock`, linux `$XDG_RUNTIME_DIR/terminal/server.sock`, dir+sock 0700/0600; Windows named pipe `\\.\pipe\terminal-rs`):
  - Control: 4-byte LE length + JSON (`serde_json`, version field `v:1`). Requests mirror the existing Request ops (serde on the op structs + `LayoutState`). Replies correlate by `rid` (snapshot, foreground_dir, init).
  - Events: `LayoutEvent` JSON; `CreatedPane`'s ServerBlock becomes an ipc block token + notice; the window shows the same fallback notice, and its block is an `IpcBlock: PaneIo` driven by the data channel.
  - Data: raw PTY bytes per block, framed `[LE length][u32 block token][bytes]`; a data frame type `snapshot` precedes raw data on attach (block snapshot as VT, same exporter).
- **Process**: `terminal server` subcommand (same binary): server thread + connection accept loop. The window tries to connect; if nothing answers, it spawns the server detached and retries.
- **Session survival**: closing the window does NOT send Shutdown; the server keeps running headless. Restarting the window attaches with `Attach` (control op): replies with the current `LayoutState` + per-block snapshots, then live events keep flowing. S3 keeps a single client connection (second connection refused until the first disconnects).
- **Robustness (folds the deferred advisories in)**: A3 blocking PTY write — per-block writer thread with a queue; A4 server panic — catch_unwind around request handling, the process keeps serving (and a panic log line).
- Testing: all existing tests stay in-process through the link abstraction; framing gets encode/decode round-trip tests (no sockets), plus a socket-level integration test for the control framing marked `#[cfg(unix)]` (Windows CI exercises the same framing over the transport abstraction).

## S4 design (locked 2026-11-12)

Multiple clients over the same server: many readers, one input writer; sessions come and go.

- **Driver policy**: at any moment exactly one session is the *driver* (input writer + layout mutator + resize authority). The most recently ATTACHED session takes the driver role from the previous one (interactive windows expect to take over); the demoted session is notified with a `DriverChanged` event and keeps working as a viewer. Server-side gating: `Write` and layout-mutating ops from a non-driver session are dropped (no error noise); read-only ops (snapshot, foreground_dir) are served for anyone.
- **Resize policy**: the server stores the driver's window area (from the driver's resize/layout ops). Only the driver's `Resize`/layout ops are applied (PTY grid follows the driver); viewer windows render scaled locally and never resize the shared PTYs.
- **Events to all sessions**: the broadcast fan-out goes to every live session's event channel (registry of per-connection senders, registered at attach, unregistered at disconnect). Viewer sessions rebuild their projections from the same state events; their client-side terminals are already per-window, so scrollback stays independent (snapshot on attach + own vt state).
- **Session plumbing**: the Busy gate from S3 goes away. Per-connection state moves from `ProcessShared` single-slot fields into a session registry (conn id → event sender, driver flag). Blocks/views keep the router ownership; a session teardown only unregisters, views live across sessions.
- **Headless exit-notice fix (known T3 gap)**: `ProcessShared.exited: Vec<PaneId>` records panes whose block exited while unobserved (or whose Exited a session missed); the Attach reply gains `exited: Vec<PaneId>` (cleared once delivered) and live sessions get normal PaneExited events.
- **A-T2b-2**: `init_layout`'s rollback no longer decrements `next_pane_id` (the id is burned, per the field doc).
- Testing: two-client unix-socket tests (driver input reaches the pane, viewer Write dropped, DriverChanged on take-over, layout events to both), driver disconnect handover, attach-with-exited list, id-not-reused after rolled-back init. In-process tests unchanged.

## S5a design (locked 2026-11-12)

Remote read/write access over the tailnet via `tailscale serve` in front of the existing server; identity from Tailscale; owner-only by default.

- **Shape**: an HTTP/WebSocket gateway process (same binary, `terminal gateway` subcommand) that connects to the local `terminal server` as a regular client and serves remote clients over WebSocket. tailscale does the transport (`tailscale serve --bg` in front of the gateway's localhost HTTP port) and identity: the gateway trusts `Tailscale-User-Login` / `Tailscale-User-Name` headers that `tailscale serve` injects (headers only survive trusted tailscale-local traffic), so auth = allow-list check, default owner-only (`remote.allow = ["<owner login>"]` config; empty = deny-all). HTTPS comes free from tailscale.
- **Protocol**: reuse the existing wire over WebSocket — control/data frames become WebSocket binary messages with the same 1-byte type prefix from S3 (control=0/data=1/data-snapshot=2, JSON payloads identical), so client logic (IpcBlock, state application) is shared between the local client and the web client. Replies/events flow server→client; requests client→server.
- **Gateway session = one driver session** per remote client, reusing the S4 registry/driver machinery unchanged (no code fork): a remote client attaches like a window, becomes driver, previous driver demoted. Single input writer policy already enforced server-side.
- **Gateway policy**: exactly one remote connection at a time (gateway-level gate; local windows unaffected).
- **Client read-only mode for viewers** is NOT part of S5a (S5 keeps it simple: remote = driver or nothing).
- **Testing**: wire-over-websocket framing tests with a real local WS server (loopback, no tailscale) exercising attach→write→readback→events; header-based allow/deny list tests; gateway↔server over the existing unix socket harness. tailscale itself is never spawned in tests.
- Out of scope for S5a: `terminal web` browser client (stage 6 CLI only covers automation), embedded tailscale (S5b, optional).

## S6 design (locked 2026-11-12)

Automation CLI over the existing IPC: `terminal ls|attach|send|capture`, talking to the live server without a window.

- **Control-plane automation family**: new request ops `AutomationList` (reply: pane id, grid, alive/dead, program command line if the server tracks it — keep to pane id/grid/alive to start), `Send { pane|block, bytes }`, `Capture { pane|block, format }` (reply: screen as text via the existing plain formatter, or VT). These are served server-side DIRECTLY on the blocks, deliberately bypassing the S4 driver gating: an automation CLI is an explicit local act (socket access = local trust), and gating it behind the window driver would make automation useless next to a window. Documented at the handler.
- **Connection handling**: every CLI subcommand opens a short-lived client connection (same endpoint resolution + spawn-if-absent as the window), sends its op by rid, prints the answer, closes. No session registration needed server-side beyond the request (the CLI never sends events back; if the registry requires a session record, register+unregister around the ask).
- **`terminal attach <id>` interactive**: connects, subscribes the block's data channel (Snapshot frame served first like any client), puts the local TTY in raw mode, forwards stdin as Send bytes and streams data frames to stdout; exit on Ctrl-C/EOT from the frame stream end (document the exact escape). This is read/write automation, still not a driver — the window keeps ownership of layout.
- **Testing**: ls/send/capture over the unix-socket harness (block created via test helper); capture reply matches the plain exported screen; send prints in the block's terminal; attach streams stream data; run windows-free. Windows: CLI paths compile (same cfg gates as the harness).
- Out of scope: scripting/auth keys beyond socket trust, remote automation (that would ride the gateway later).

## Environment notes (this machine)

- The user's zsh wraps `cd` with `eza` and aliases `cp` to an interactive form: both hang non-interactive shells. Use absolute paths, `--manifest-path`, `git -C <repo>` and `/bin/cp -f`.
- macOS build needs Zig 0.15.2 (`zig@0.15`, keg-only) and Xcode's default toolchain (`xcrun --kill-cache` if linking fails with `Argument list too long`).
- In debug builds libghostty runs in Zig Debug mode: scrolling output costs about 250 ms per KB, so PTY flood tests use non-scrolling output such as `yes "$(printf 'x\033[H')"`.
- ConPTY (Windows) asks for the cursor position (`ESC[6n`) at startup and shows nothing until it is answered: tests that read raw PTY output must answer `ESC[1;1R`.
- `libghostty_vt::Terminal` is not `Send`: whoever owns terminals builds them on its own thread.
- Commit messages: Conventional Commits, no `Co-Authored-By` and no AI attribution. Push, PR and merge are the user's decisions.
